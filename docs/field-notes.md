# 현장 노트 — 이 코드가 지금 모양이 된 이유

각 항목은 실제 운영 중 일어난 일이고, 코드의 어느 부분이 그 대응인지 함께 적었습니다.

## 1. CO₂ 0 ppm — "없는 값"이 데이터가 된 사고

- **증상**: 대시보드에서 CO₂ 값이 잠깐 보였다가 사라졌습니다. 확인해 보니 한 노드는 하루 2,764개 표본 중 **유효 값이 11개**, 나머지는 모두 0.0 ppm이었습니다.
- **원인**: SCD41은 새 표본이 없을 때 측정값 대신 0을 돌려주고, 그 0은 CRC 검사를 통과합니다.
  드라이버는 처음 한 번만 "준비됨"을 확인하고 이후에는 확인 없이 읽고 있었습니다.
- **대응**: 매번 준비 여부 확인, CO₂ 0 거부, 실패는 예외로 드러냄. 잘못 쌓인 5,880행은 승인을 받아 삭제했습니다.
- **교훈**: 결함 하나가 아니라 **"장치가 CRC를 통과하는 자리 표시 값을 주면 값으로 취급하지 않는다"는 규칙**으로 고쳐야
  같은 종류의 다른 결함(저울 대체값, 습도 0으로 자르기 등)도 함께 사라집니다.
- **코드**: `python/edgekit/sensirion.py`, `python/edgekit/reader.py` (센티넬 대신 `None`), `cpp/src/sensirion.cpp`

## 2. 센서가 조용히 멈춰 7주 동안 표본이 거의 없음

- **증상**: 노드는 온라인이고 다른 센서는 정상인데, CO₂만 하루 0~61개 표본(정상 약 2,800개). 재부팅 직후 몇 분만 값이 나왔습니다.
- **원인**: 순간 전원 저하로 센서가 리셋되면 대기 상태로 깨어나 측정 시작 명령을 다시 받아야 하는데,
  드라이버는 이미 시작했다고 기억하고 있었습니다.
- **대응**: 정해진 시간 동안 새 표본이 없으면 시작 상태를 버리고 다시 초기화합니다. 이 재초기화가 자동 보정(ASC)을 다시 끄는 유일한 경로이기도 합니다.
- **코드**: `Scd41.read()`의 `restart_after_s`, 테스트 `test_sensor_reset_to_idle_is_recovered_automatically`

## 3. 자동 보정이 밀폐 챔버에서 값을 끌어내림

- **원인**: SCD41의 자동 보정은 "일주일 중 최저값 = 바깥 공기 400 ppm"을 가정합니다. 농산물이 호흡하는 밀폐 챔버는 최저값이 그보다 훨씬 높아,
  센서가 자기 값을 수백 ppm씩 낮춥니다. 예외도 오류도 나지 않습니다.
- **대응**: 시작할 때마다 자동 보정을 끄고, **센서가 돌려준 설정값을 되읽어** 상태로 보고합니다(보낸 값이 아니라).
- **코드**: `Scd41._disable_asc()`, `asc_enabled`

## 4. USB-RS485 어댑터 재연결 — 실행된 적 없는 복구 코드

- **증상**: USB 어댑터가 다시 인식되면 기존 포트 핸들이 계속 입출력 오류를 냅니다. 재연결 코드가 있었는데도 수집이 멈춰 있었습니다.
- **원인**: 복구 코드는 `OSError`만 잡았는데, 이 오류는 `termios.error`로 올라오고 `termios.error`는 `OSError`가 아닙니다.
  현장 로그의 오류 문자열 형식에서 이를 알아냈습니다.
- **대응**: 두 예외를 모두 잡고, 핸들을 버린 뒤 같은 호출에서 한 번 다시 엽니다. 장치 경로는 재인식 후에도 바뀌지 않는 by-path 링크를 씁니다.
- **코드**: `python/edgekit/transport.py`의 `SERIAL_IO_ERRORS`, `cpp/src/transport.cpp`의 재시도

## 5. 26시간 통신 두절 — 데이터는 남았다

- **상황**: 현장 회선이 26시간 끊겼고, 알림은 꺼져 있어 아무도 몰랐습니다.
- **결과**: 엣지가 모든 측정을 먼저 로컬 SQLite에 저장하고 있었기 때문에, 복구 후 **28,657건이 순서대로 재전송**되어 손실이 없었습니다.
- **추가한 것**: 두절이 더 길어져 저장 공간이 찰 때를 대비해, 가장 오래된 미전송분부터 버리는 상한.
- **코드**: `python/edgekit/outbox.py`

## 6. 설정 하나로 전 노드가 재시작할 수 있던 구조

- **원인**: 운영 화면에서 바꿀 수 있는 폴링 상한(30초)이 systemd 워치독 시간(30초)과 같았습니다. 주기를 조금만 올려도 워치독이 프로세스를 죽이고,
  설정은 모든 노드에 동시에 적용되므로 전체가 재시작을 반복하게 됩니다.
- **대응**: 상한을 낮추고, 서버 쪽에도 상한을 두고, 두 값의 관계를 테스트로 묶었습니다.
- **교훈**: 서로 다른 파일에 있는 두 숫자의 관계는 리뷰로 지켜지지 않습니다. 테스트로 묶어야 합니다.
